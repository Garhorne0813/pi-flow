# Issue #1：SSE 查询与 Run 心跳混合负载

2026-10-09，本地 Node.js 24 + Docker PostgreSQL 17.11；单个 635,900 字节 JSONB 租户，连接池上限 10。100 个读客户端每 250 ms 运行 SSE 相同的 Run ACL/事件过滤回调，4 个客户端每 1 s 执行 Run 授权检查与租约续期写事务。两轮使用相同随机历史负载，在专用租户运行并清理；每轮计划发送 5 秒，统计时间包括排空已提交请求。旧路径调用仍保留的 `tx`，新路径调用 `read`，两者使用相同 PostgreSQL 和回调。

| 指标 | 旧路径：tx | 新路径：read |
| --- | ---: | ---: |
| 统计窗口（含排空） | 7,977 ms | 5,310 ms |
| 完成轮询数 | 269 | 1,497 |
| 完成轮询吞吐 | 33.7/s | 281.9/s |
| 轮询 P95 | 3,039.2 ms | 401.5 ms |
| 心跳 P95 | 3,109.8 ms | 1,067.6 ms |
| 心跳 UPDATE 数 | 8 | 20 |
| 整租户 UPDATE 数（revision 增量） | 277 | 20 |
| 轮询导致的 UPDATE 数 | 269 | 0 |
| 观察到行锁等待的采样数 / 总采样数 | 353 / 356 | 52 / 120 |
| 最多等待锁的后台连接数 | 9 | 3 |
| 累计后台锁等待估算 | 69,104 ms | 4,279 ms |

只读轮询的 UPDATE 数降至 0，写事务仍用于心跳。新路径的锁等待来自多个心跳写事务之间的竞争；JSONB 全量读取、解析和共享连接池仍会影响延迟，新路径本轮未达到理论 400 次轮询/秒。这是单机短时对比，不是生产容量承诺。

> 2026-10-10 复测说明：上表是 Runs/Sessions/Events 拆表前的历史结果。拆表后 Run 心跳直接更新 `harness_runs`，不再改写租户行，因此两种轮询模式下租户行都应保持零写入；`scripts/bench-store-reads.mjs` 的断言已同步。最新复测记录为旧路径 53.7 轮询/s、轮询 P95 1,902 ms；新路径 389.2 轮询/s、轮询 P95 257 ms。该数据来自单机短时测试，不代表生产容量保证。

锁等待每约 20 ms 通过独立连接读取 `pg_stat_activity` 中针对 `harness_tenants` 的 Lock 等待数量，并按实际采样间隔积分；累计数是各后台连接等待时间之和，允许大于墙钟时间，属于近似采样指标。事件循环负载使采样间隔可能变长。吞吐分母包含排空时间，P95 从发起调用到回调返回计量，包含池队列等待。请求完成审计、HTTP/SSE 编码、Worker 调度与空闲 GC 不包含在此存储层基准中；真实 SSE 的顺序、游标与 ACL 另有 API 回归测试。请求完成审计仍每个请求写一次，SSE 轮询本身不写。

复现（使用已迁移的专用测试库）：

```bash
npm run build
TEST_DATABASE_URL=postgres://user:password@localhost:5432/test npm run bench:store:reads
# 可选：BENCH_DURATION_MS=10000；最短 2500 ms
```

脚本不会打印连接串或执行迁移；创建独立随机租户，结束时删除。数据库日志/统计工具可另行验证 WAL、UPDATE 和锁等待。Events/Runs/Sessions 拆表与通知推送仍是后续性能工作。
